    B01 / HIGH
    Reproduced in browser

    A failed checklist request displays “ready”

    A simulated server error on an empty job produced “Nothing missing — this job is ready to hand over.” An unavailable check is currently treated as a successful check with no missing items.

    Checklist requestHTTP 500 on an empty job
    →
    Error handlingMissing data becomes an empty gap list
    →
    Displayed resultReady to hand over

    Needed change: distinct loading, unavailable and checked states. Show readiness only after a successful response for the current job.

    Reproduction and source

    Intercepted the handover request in Chrome and returned HTTP 500. Created a fresh project through New job. The project had zero runs; the panel still displayed ready. This was an error-injection test in the temporary database.

    B02 / HIGH
    Reproduced in domain code

    Partial specifications count as complete

    On a 5-metre run, specifying height for just the first metre produced no missing-height warning. A model assigned to just the first metre also cleared the missing-model check without a project default.

    1 m stated4 m not stated

    Actual result in both checks: no handover gaps.

    Needed change: validate coverage across every required interval and run, accounting for explicit project defaults, instead of checking whether any event exists.

    Reproduction and source

    Used the existing complete-job fixture. In separate cases, shortened the height interval to 1,000 mm or removed the project model and assigned a model only from 0 to 1,000 mm. Both calls to handover_gaps() returned an empty list. These were direct function checks, not additional browser screenshots.

    handover.py:84 and :95 · Recorded reproduction

    G01 / SCOPE DECISION
    Missing MVP capability

    The original sale evidence cannot accompany the job

    The current salesperson flow has no attachments for the signed contract, original drawing, photos or WhatsApp material. The checklist reached ready without those sources.

    Proposed next step: agree on a minimum evidence package, then add job-level attachments. Linking evidence to specific stretches can follow separately.

    Observed boundary

    No visible file input or source-attachment flow was found in the role. Ready without source attachments · Current screen structure

    G02 / SCOPE DECISION
    Missing MVP capability

    There is no explicit transfer to the office

    A saved project and an in-page checklist exist. The salesperson cannot mark a handover submitted or see that the office received it; a tracked clarification loop is also absent.

    Proposed next step: define the smallest submission and receipt workflow, including what happens when the salesperson changes the job afterward. Office acceptance criteria remain a decision.

    G03 / SCOPE DECISION
    Missing structured details

    Some sold specifications only fit in notes

    No dedicated agreed-finish field or gate-opening-direction control was found in this salesperson flow. Notes can preserve them, but the current checks cannot assess whether they are complete.

    Proposed next step: list the specifications that actually appear in your signed sales, then add only the fields the office needs to interpret them reliably.

    Actual gate form

    Width and kit fields. The earlier prototype's inward/outward selector was a proposal, not an existing control.

    U01
    Proposed UI improvement

    Keep handover status visible

    For the office sits below a long sidebar, after technical site conditions and run events. Move a compact readiness status near the job identity, with the full checklist accessible from it.

    U02
    Proposed UI improvement

    Let missing items open the relevant editor

    A missing-height item should name and select the affected stretch, then open its Height control. The existing checklist reports counts and sentences without taking the user to the required edit.

    U03
    Proposed UI improvement

    Give the selected stretch a readable summary

    Height, base, model and gates are spread across tools and technical event entries. Present their recorded values together, with direct edit actions and explicit unknowns, while retaining the existing drawing tools.

    U04
    Proposed UI improvement

    Clarify sales facts versus office decisions

    HVHZ, code edition, post orientation and raw AI intent names remain visible to sales. Decide who owns each input; keep the salesperson's required work focused on the agreement and observed site conditions.

    Observed examples

    Site conditions · Base orientation · AI intent terminology

    U05
    Proposed UI improvement

    Distinguish saved values from entry defaults

    Reopened forms can offer defaults rather than the recorded specification. Make “add another interval” distinct from “edit this saved value,” and prefill an edit with its current data.

    Evidence and limit

    The Height form seeds 1,800 mm; the Base surface list initially selects soil. Reopened dialog captures were cancelled, so they are not screenshots of overwritten saved values. editor.js:846 and :870

    U06
    Proposed UI improvement

    Align pricing prominence with a signed sale

    The sale is already signed, yet onboarding mentions a quote and generation remains prominent. Define whether this estimate serves an internal check, then adjust its label and position. Live quoting is outside the agreed MVP scope.

    Suggested order: fix B01-B04 first; agree the evidence package and office transfer in G01-G02; then improve the existing screen in small, reviewable changes. These are recommendations, not an approved implementation plan.
